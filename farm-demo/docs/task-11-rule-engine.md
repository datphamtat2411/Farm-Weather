# Task 11 — Cloud rule engine and alarms
Chapter 5 §5.3.1–5.3.2, Table 5.7. Native ThingsBoard rule chains are provisioned on the farm station and gateway profiles, with the platform root left untouched. Queue must be SequentialByOriginator. The STM32's confirmed status bits are authoritative (not inferred from five-minute averages). Alarm types: WIND_HIGH/CRITICAL, RAIN_HIGH/MAJOR, TEMPERATURE_HIGH/MAJOR, BATTERY_LOW/WARNING, SENSOR_FAULT/MAJOR, DATA_STALE/MAJOR, BUFFER_NEAR_FULL/WARNING. Each uses native create/update and clear nodes. The Notification Center sends WEB notifications to the tenant administrators on creation, not every sample. Existing user/role configuration is deferred to Task 12.
- Edge identifies fresh versus historical records and prevents older buffered events from overwriting a newer known state; routing flags are stripped by the rule chain. Original timestamp and keys are preserved in the history-only Save Timeseries node. Device-profile routing leaves other platform traffic on the original root chain.
- Durable server attributes store the last confirmed sequence/timestamp, current status, last periodic sample and expected period. The same sequence cannot produce a second active alarm. Ack is distinct from clear. A newer live periodic/event confirms the current state. Gateway buffer health is published from actual SQLite diagnostics; warning starts at >=80%, clears <70%. This does not estimate physical STM32 Flash occupancy.
- Run provision.py with optional --watchdog-token-output outside the repository. Run cloud/watchdog.py as an independent cloud process with FARM_WATCHDOG_STATION_TOKEN set from that private file and --host/--ca-file. It emits only watchdog ticks via MQTT/TLS, never weather observations. Cloud evaluates measurement timestamps, not MQTT connectivity; ticks cannot refresh measurement age. In this demo a tick uses the station's token; dedicated least privilege and production deployment are Task 12. Start the watchdog on the Cloud, not the farm Edge, so that a 4G outage does not stop checks.
- CI tests real TB alarm API and TLS gateway MQTT, not a fake alarm service. The stale test ages the persisted measurement watermark in the isolated CI instance rather than waiting 30 minutes. Native notifications are verified via the API. Evidence is rule-engine-report.json. No claim of actual radio or hardware simulation here.
- No new RPC, RBAC or Dashboard work in this task. No direct SQL writes. Multi-node Rule Engine operations are not one database transaction; the current-state cursor and native alarm state are persisted in ThingsBoard. Queue and edge retry semantics are distinct from exactly-once side effects.
